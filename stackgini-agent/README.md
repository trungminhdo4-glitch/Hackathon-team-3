# Stackgini procurement research agent

Give it the URL of an unfamiliar software product. It investigates the product and vendor on the open web and returns a GREEN, YELLOW or RED procurement verdict with flags, reasoning, validated evidence, unresolved questions and limitations.

It runs on your logged-in Claude Code subscription through `claude -p`. No API keys. No paid search or scraping APIs.

## Live-round verdicts: `stackgini-verdicts.csv`

How to read it: one row per product, in the column layout of the labelled set (`id,url,product,vendor,overall,green_flags,yellow_flags,red_flags,reasoning`), with `overall` = Green / Yellow / Red. Each reason inside a flag column is separated by ` | ` and ends with `Sources:` followed by the URL(s) it was checked against. Only reasons whose cited source was re-downloaded and matched by the agent are listed as flags. Three extra columns come last: `confidence`, `investigation_status` (COMPLETE / PARTIAL: some research questions stayed open), and `unsupported_observations` (agent observations it could not back with a checked source; not used as reasons). `stackgini-verdicts.json` adds the evidence passages; `stackgini-verdicts.md` is a readable version. Generated by the agent (`main.py compete`, then `main.py export`); nothing was researched by hand.

## Setup

Python 3.11+ (tested on 3.14.7) and an authenticated Claude Code CLI (`claude auth status` in a normal terminal shows `loggedIn: true`, `authMethod: oauth_token`).

```bash
cd ~/stackgini-clean
```

```bash
.venv/bin/pip install -r requirements.txt
```

```bash
.venv/bin/python main.py doctor --live
```

`doctor` checks the CLI, auth (using the same allowlisted environment as research calls), packages, the dataset and direct HTTP. `--live` runs one small call with the exact research runner configuration and reports separately: model errors, auth source, session tools, MCP/plugin isolation, WebSearch and WebFetch calls counted from stream events, failed fetches, permission denials and structured output.

## Live round (recommended)

Put the products in `live.csv` (`id,url`). Then, with the remaining minutes until the cutoff:

```bash
mkdir -p reports/live && .venv/bin/python -u main.py compete --input live.csv --output reports/live/submission.json --minutes 40 --concurrency 4 2>&1 | tee reports/live/compete.log
```

- Phase A: every product gets an initial verdict (soft 5.5 min, hard cap 8 min each; follow-up only for RED-grade findings that lack a retrieved source; critic only for RED, guardrail changes, conflicts and LOW-confidence GREEN; no Opus).
- Phase B: the remaining time goes to the products most likely to change (failed, partial, low confidence, weakly sourced RED, contradictions, unreviewed RED/GREEN), each capped at 7 min. A phase B result replaces phase A only if it completes.
- The last 270 s are reserved; nothing new starts when under 120 s of work time is left.
- Interim checkpoints are saved as soon as a validated verdict exists; a product cancelled later keeps that verdict as PARTIAL. Products with no usable research are FAILED, never-started ones NOT_STARTED; both are placeholders, not findings.
- `submission.json/.csv/.md` are re-exported atomically after every product, so a valid file exists at any time. Progress: `reports/<run_id>/run_state.json`.

Monitoring during the run (second terminal):

```bash
tail -f reports/live/compete.log
```

```bash
cat reports/live/submission.md
```

The live log lines show `[T+mm:ss | Ns left]`, each product's phase start/finish, verdict and status; `reports/<run_id>/run_state.json` lists every product's status, verdict, confidence and seconds. Reasons are exported only with sources they were explicitly linked to; everything else is in the `unsupported_observations` column.

Resume after a crash, Ctrl-C or subscription limit (pass the minutes still left):

```bash
.venv/bin/python main.py compete --input live.csv --output reports/live/submission.json --resume RUN_ID --minutes 20 --concurrency 4
```

Fallback (the earlier, single-phase batch path; or the untouched copy in `fallback_v1/`):

```bash
.venv/bin/python main.py batch --input live.csv --output reports/live/submission.json --mode fast --concurrency 4 --deadline-minutes 36 --no-cache
```

## Pipeline

```
URL -> safe URL check -> [HTTPX website snapshot | RDAP | Wayback] (+ GitHub if linked)
-> ONE bounded Claude research session (identity, claims, 12-criterion baseline,
   autonomous follow-ups, preliminary verdict, optional tool_requests)
-> independent evidence validation (re-download, literal quote check, entity, independence)
-> coverage + material-gap ranking -> [Python runs requested tools -> resumed follow-up round]*
-> guardrails -> adversarial critic (when triggered) -> optional Opus escalation
-> change review -> final guardrails -> JSON + Markdown report -> submission export
```

Python owns deadlines, concurrency, coverage, validation, persistence, caching, error handling and evaluation. Claude owns understanding the product, choosing queries, following leads, interpreting evidence and the verdict itself.

Research is one Claude session per product rather than one per criterion. The context gets built once. The critic is a second, short session fed a compact JSON summary of validated evidence, never the research transcript, which keeps cache-read tokens down.

## What makes the evidence trustworthy

The runner records the tool events Claude Code actually emitted (`stream-json`). The validator then re-downloads every cited URL itself (HTTPX + BeautifulSoup, PDFs via pypdf, SSRF-checked, cached, max 2 concurrent requests per domain) and grades each citation:

| Status | Meaning | Can carry |
|---|---|---|
| ORIGINAL_SOURCE_VERIFIED | excerpt found literally (normalised case/whitespace/quotes) in text we retrieved ourselves, or in a specialised public-API result | decisive RED / GREEN points |
| SOURCE_CONTENT_RETRIEVED | source retrieved and about this entity; excerpt matched only approximately (`quote_match: approximate`), or literally only in model-processed WebFetch output | decisive points |
| SEARCH_SNIPPET_MATCHED | excerpt literally in the search-result text for that URL; page never checked | supporting flags; a RED needs 2 independent ones |
| SEARCH_OBSERVED | URL appeared in search results; content unchecked | a lead only, labelled as such |
| UNVERIFIED | source exists, excerpt not locatable | a lead only |
| REJECTED | never observed and unretrievable, unsafe, a page about a similarly named entity, or a quote absent from substantial retrieved text | nothing |

The located passage is stored in `source_passage`, separate from the model's interpretation (`about`). Approximate matches are never called verbatim. Entity checks need the full product/vendor name, the official domain label, or two distinctive name tokens, so a similarly named company does not count. Duplicate URLs are merged; syndicated text and the vendor's own domain are not independent (`independence_group`), and findings report how many independent groups support them.

Guardrails in `research/judge.py` (integrity only, never taste):

- A red flag must cite usable evidence or it moves to unresolved questions.
- A RED verdict needs a retrieved (decisive) source, or two independent snippet-level sources; otherwise YELLOW, LOW confidence.
- A GREEN verdict needs at least one retrieved positive source; insufficient evidence is not GREEN.
- Confidence is capped by coverage and validation rates.
- A critic verdict change needs an explicit justification (challenged conclusion, what was missing or misread, impact) that relies on evidence that validated; upgrades toward GREEN need retrieved evidence.

## Coverage and follow-ups

Each criterion gets `research_status` VERIFIED / PARTIALLY_VERIFIED / UNRESOLVED / NOT_APPLICABLE from executed queries and evidence quality. `material_gaps()` ranks unresolved high-impact criteria and RED/YELLOW findings resting only on leads or snippets. Any material gap, or any specialised-tool request by the model, triggers a resumed follow-up round, whatever the search count (FAST: 1 round, DEEP: 2). Rounds stop at the per-product time budget.

## Specialised tools

Python runs these against fixed public endpoints, no API keys. The model cannot call them directly: it lists `tool_requests` in its report; Python validates tool name and argument against an allowlist and pattern, executes at most 6 (FAST) or 10 (DEEP), and resumes the session with the results. Results are also handed to the validator as independently retrieved text, so a citation of them can be checked literally.

| Tool | Source | Run |
|---|---|---|
| rdap_domain | rdap.org (registry RDAP) | always, product domain |
| wayback_history | Wayback CDX API: earliest/latest snapshot, years archived | always, product domain |
| github_repo | GitHub REST API: archived flag, last push/commit, releases, licence | automatically if the home page links a repo; or on request |
| osv_vulnerabilities | api.osv.dev, exact Ecosystem:package | on request |
| nvd_cves | NVD 2.0 API, exact phrase, filtered to CVEs naming the product | on request |
| fetch_document | SSRF-checked direct page/PDF retrieval | on request |

Tool failures (rate limits, timeouts) are recorded as limitations and never treated as evidence about the vendor.

## The rubric

`prompts/investigator.md` holds the decision rubric as general procurement principles: core promise first, misconduct versus incident, allegation versus established finding, appearance as a weak signal both ways, vendor identity and checkable social proof, a bar that rises with data sensitivity and privilege, lifecycle, ownership effects on this product, licensing ambiguity, incident handling, team capacity, implausible metrics. It contains no product names, URLs, labels or dataset rows. The earlier version was derived from the full 40-row dataset; rules that read like specific withheld examples were rewritten as general principles.

## Subscription use and safety

- Every Claude call runs with `--safe-mode`, `--tools WebSearch,WebFetch`, the same allowlist, an explicit deny list (Bash, Read, Write, Edit, Agent...), `--permission-mode dontAsk --permission-prompts none`, an empty `--strict-mcp-config`, and `--disable-slash-commands`, from an empty scratch directory. Bypass mode is never used. Verified from the CLI's init event: tools `StructuredOutput, WebFetch, WebSearch`, `mcp_servers: []`, `plugins: []`, `skills: []`.
- `--setting-sources ""` is NOT used: on CLI 2.1.268 it hides the OAuth login and every call returns "Not logged in · Please run /login". That was the cause of the earlier zero-tool doctor runs.
- The child environment is an allowlist (HOME, PATH, locale, proxy and CA variables). Every `ANTHROPIC_*` and `CLAUDE_*` variable (API key, auth token, base URL, Bedrock/Vertex switches, parent-session markers) is dropped, so a stray key or provider setting cannot switch billing. A run whose `apiKeySource` is not `none` raises `AuthError`.
- A result counts as failed when `is_error` is true, `terminal_reason` is an error or `api_error_status` is set, whatever `subtype` says (the CLI reports auth failures as `subtype: success`). Auth failures raise `AuthError`; usage limits raise `SubscriptionLimitError` and stop the batch.
- Tool calls are counted from stream events. The result's `server_tool_use` counters were observed to stay 0 even when both tools ran.
- The prompt goes through stdin. No `shell=True`.
- Website content and tool results are wrapped in untrusted blocks whose closing tags are stripped; prompts forbid following instructions found in them.
- The HTTPX fetcher allows only public http(s) on standard ports, re-checks every redirect hop, rejects private, loopback, link-local, CGNAT, metadata and IPv4-mapped addresses, judges NAT64 (`64:ff9b::/96`) addresses by their embedded IPv4, and caps size (2 MB HTML, 8 MB PDF), time and per-domain concurrency.
- `total_cost_usd` is an API-equivalent list price, not a subscription charge.

## Modes

| | FAST | DEEP |
|---|---|---|
| research max turns | 30 | 60 |
| search guidance | 10-18 | 20-35 |
| follow-up rounds (gap-driven) | 1 | 2 |
| specialised tool requests | 6 | 10 |
| critic | when triggered | always |
| Opus escalation | contested verdicts, budget 2 per batch | same |
| per-call timeout | 420 s | 900 s |

`--product-minutes N` sets a soft per-product budget: optional follow-up and critic rounds are skipped when it is nearly used. In a batch with `--deadline-minutes`, each product's budget is derived from the time left, 45 s are reserved for export, and products that cannot finish are not started.

## Caching

SQLite in `data/stackgini.sqlite3`: fetched pages (72 h TTL), completed reports keyed by URL + mode + model (7 days, so security and lifecycle findings are not reused as current indefinitely), validated evidence per run, and batch run state for resume. Use `--no-cache` to force fresh research.

## Submission format

The official brief (`challenge-brief.pdf`) asks for "a file with your agent's verdicts" next to the standard AIB submission, judged on the calls and on evidence ("every reason points to a source that says what the agent claims"). It fixes no columns. The export therefore keeps the column layout of the organisers' labelled examples so their comparison script can read it, `id,url,product,vendor,overall,green_flags,yellow_flags,red_flags,reasoning` with `overall` as Green/Yellow/Red, expands every evidence id in a flag into the source URLs a human can open, and appends `confidence,investigation_status,sources`. Products that were not investigated still get a row, marked `NOT_STARTED`, with reasoning saying it is not a finding (`--no-placeholders` omits them).

## Known limitations

- Playwright rendering and screenshots are not implemented. Visual-only signals are invisible; JS-rendered sites are noted as a tooling limitation.
- NVD is often rate limited without a key; failures are recorded, not interpreted.
- WebFetch returns model-processed text, so a quote found only there is SOURCE_CONTENT_RETRIEVED, never ORIGINAL_SOURCE_VERIFIED. Sites that block HTTPX keep their evidence at that level.
- A product cancelled at a hard batch deadline loses its partial research (it is marked pending and can be resumed).
- Run-to-run variance is real; DEEP mode with the critic always on is the mitigation when a verdict matters.
